# Feature: Auto-generate FB signal flow diagrams from SCL code

## IMPORTANT: This is a NEW feature — FB flow diagrams only

This has NOTHING to do with the process sequence diagrams in the matrix review step. Do not modify `src/lib/process-sequence-diagram.ts` or anything related to process sequences. This is a separate visualization for reviewing Function Block code in the device code step of the wizard.

Discard any previous flow diagram work that mixed FB diagrams with process diagrams. Start fresh.

## What this does

When an engineer is reviewing a generated FB artifact in the device code step, they can see a visual signal flow diagram showing how inputs flow through internal logic to outputs. The diagram is auto-generated by parsing the SCL code of the FB.

## Where it lives

- New file: `src/lib/fb-flow-diagram.ts` — parses SCL and generates the diagram data
- New file: `src/components/forge/fb-flow-renderer.tsx` — renders the diagram as SVG
- Integrated into: `src/components/forge/forge-code-viewer.tsx` (or wherever the artifact preview lives in the device code step) — as a tab or toggle alongside the code view

## Diagram style

### Layout: Columns per output

The diagram uses COLUMNS — one per output (VAR_OUTPUT). Each column traces vertically from its source inputs at the top down to its output hexagon at the bottom. This lets an engineer trace any output straight up to see exactly what feeds it.

When an FB has many outputs, split into multiple diagram pages/sections:
- Group 1: Primary control outputs (e.g. #runForward, #runReverse)
- Group 2: Fault outputs (e.g. #runFault, #stopFault, #faulted, #error)
- Group 3: Status/monitoring outputs (e.g. #busy, #idle, #status)

Each group gets its own diagram with a title.

### Node shapes

All nodes use RIGHT-ANGLED connections only — no diagonal lines, no curves. Every connection is either vertical or horizontal, with 90-degree bends where direction changes.

- **VAR_INPUT**: Rectangle with small border-radius (rx="6"). Shows `#varName = TRUE` or `#varName`
- **Condition/decision**: Rectangle (rx="6"). Shows the condition like `#_Forced_Ctrl = FALSE`
- **Timer/counter output**: Rectangle (rx="6"). Shows `#timerName.Q = TRUE`
- **Static variable (intermediate)**: Pill shape (rx = half height). Shows `#varName`
- **VAR_OUTPUT**: Hexagon. Shows `#_OutputName`
- **Self-hold / feedback loop**: Dashed arrow that loops from a variable back to itself

### Colors

Use CSS variables for dark mode compatibility:

- **Input nodes**: Use a blue-tinted style — `fill` from `c-blue` ramp (50 stop in light, 800 in dark), border from 600 stop
- **Condition/decision nodes**: Use a purple-tinted style — `c-purple` ramp
- **Timer/counter nodes**: Use a teal-tinted style — `c-teal` ramp
- **Intermediate variables (pills)**: Use neutral gray — `c-gray` ramp
- **Output hexagons**: Use a green-tinted style — `c-green` ramp
- **Fault-related nodes**: Use red-tinted style — `c-red` ramp (for fault latches, fault outputs)
- **Connection lines**: Use `var(--color-border-secondary)` for normal flow, `var(--color-text-danger)` for fault paths
- **AND/OR labels**: Use `var(--color-text-secondary)` — small text labels at merge points
- **Self-hold dashed lines**: Use `var(--color-border-secondary)` with `stroke-dasharray="3 3"`

### Connection rules

ALL connections must be right-angled:
- Vertical segments go straight down
- When two inputs merge (AND/OR), each comes down vertically to the same Y level, then horizontally to a common merge point, then vertically down to the next node
- When a path splits (decision), the center line goes down, then horizontal lines go left and right to the branch columns, then vertical down into each branch
- NO diagonal lines anywhere
- NO curved paths anywhere
- Minimum 20px gap between parallel horizontal runs to avoid overlapping

### Merge patterns

**AND merge** (series — both must be true, like ladder contacts in series):
A flows into B, then B flows to the next node. They are STACKED VERTICALLY, not side by side.
```
  #inputA
     |
     v
  #inputB
     |
     v
  next node
```
If there are 3 AND conditions, they chain: A → B → C → next.

**OR merge** (parallel — either triggers, like ladder branches):
A and B sit SIDE BY SIDE at the same Y level. Their lines come down to a shared horizontal merge, then drop to the next node.
```
  #inputA        #inputB
     |               |
     +-------+-------+
             |
             v
        next node
```

This matches how PLC engineers think — AND is series contacts, OR is parallel branches.

### Decision split pattern

```
         #decision?
             |
     +-------+--------+
     |                 |
  "FALSE"           "TRUE"
     |                 |
     v                 v
  left col          right col
```

The decision box has a single line going down, which splits horizontally left and right, each arm labeled, then drops vertically into the branch columns.

## SCL parsing rules

### Step 1: Extract declarations

Parse the SCL to extract:
- VAR_INPUT names and types
- VAR_OUTPUT names and types
- VAR (static) names and types — identify timers (TON, TOF, TP), edge detectors (R_TRIG, F_TRIG), and regular variables
- VAR_TEMP names

### Step 2: Trace assignments

For each VAR_OUTPUT, trace backwards through the code to find what feeds it:

1. Find the direct assignment: `#outputVar := expression;`
2. If the expression references a static variable, trace that variable's assignment
3. If the expression references a temp variable, trace that variable's assignment
4. Continue until you reach VAR_INPUT variables or constants

### Step 3: Identify logic patterns

Detect these common PLC patterns:

**Simple assignment**: `#output := #input;` → direct line from input to output

**AND combination**: `#result := #a AND #b;` → A stacked above B in series (A → B → result). For 3+ conditions: A → B → C → result. This is series contacts.

**OR combination**: `#result := #a OR #b;` → A and B side by side, merging to result. This is parallel branches.

**AND + OR combined**: `#result := (#a OR #b) AND #c;` → A and B side by side merging (OR), then the merged result flows down into C (AND series), then to result.

**NOT**: `#result := NOT #input;` → show the input node as `#input = FALSE`

**Timer call**: `#instTimer(IN := #condition, PT := #duration);` followed by `#result := #instTimer.Q;` → show condition → timer node → result

**Edge detection**: `#instEdge(CLK := #input);` → show as `#input (↑ edge)` feeding into `#instEdge.Q`

**CASE selector**: `CASE #mode OF 1: #cmd := #autoRun; 2: #cmd := #semiRun; ...` → show all case inputs side by side with mode labels, merging to the resolved variable

**IF/ELSIF chain for status**: `IF cond THEN #status := val1; ELSIF cond2 THEN #status := val2;` → show as a truth table below the relevant inputs

**Self-hold latch**: `#latch := (#setCondition OR #latch) AND #holdCondition;` → setCondition and latch side by side (OR parallel merge), then the merged result flows down in series into holdCondition (AND), then to the latch output. Dashed self-hold arrow from the latch output back up to the latch input box.

```
  #setCondition    #latch (self-hold)
       |               |
       +-------+-------+    ← OR (parallel)
               |
               v
       #holdCondition        ← AND (series)
               |
               v
           #latch  ─ ─ ─ ┐
                          │  dashed loop back
           ┌ ─ ─ ─ ─ ─ ─ ┘
           ↓ (to #latch input above)
```

**Fault latch**: `IF #faultCondition THEN #faultLatch := TRUE; END_IF;` → show condition → latch (pill)

**Fault reset**: `IF #resetEdge AND conditions THEN #latch := FALSE; END_IF;` → show as dashed arrows from the reset action back to each latch it clears

### Step 4: Group outputs into diagrams

For complex FBs, group outputs into logical diagrams:

- **Group by REGION**: If the FB uses REGION blocks, use them as grouping hints. Outputs assigned in "Output Mapping" that derive from "State Machine" variables go in the run command diagram. Outputs assigned from fault latches go in the fault diagram.
- **Group by type**: Control outputs (Bool commands) in one diagram, fault outputs in another, status/monitoring in a third.
- **Max 4 output columns per diagram** — if more, split into additional diagrams.

### Step 5: Generate SVG

For each diagram group, generate an SVG with:
- viewBox width = 680 (standard)
- viewBox height = calculated from content
- Title text at the top: "FBName — group description"
- Columns laid out left to right, evenly spaced
- All connections right-angled
- Legend at the bottom showing node shapes and colors

## Data structure

```typescript
interface FbFlowDiagram {
  title: string;
  columns: FbFlowColumn[];
}

interface FbFlowColumn {
  outputName: string;  // The VAR_OUTPUT this column traces to
  nodes: FbFlowNode[];
  connections: FbFlowConnection[];
}

interface FbFlowNode {
  id: string;
  type: "input" | "condition" | "timer" | "intermediate" | "output" | "fault";
  label: string;       // e.g. "#_Sensor = TRUE"
  sublabel?: string;    // e.g. "Physical input"
  shape: "rect" | "pill" | "hexagon";
  x: number;
  y: number;
  width: number;
  height: number;
}

interface FbFlowConnection {
  fromId: string;
  toId: string;
  type: "normal" | "fault" | "selfhold" | "reset" | "switch";
  label?: string;       // "AND", "OR", "TRUE", "FALSE"
  // All connections are right-angled — the renderer calculates the path
}
```

## Rendering

The renderer (`fb-flow-renderer.tsx`) takes `FbFlowDiagram[]` and produces SVG:

```typescript
interface FbFlowRendererProps {
  diagrams: FbFlowDiagram[];
  className?: string;
}
```

It renders each diagram as a separate SVG. Use the pre-built CSS classes from the widget system (`c-blue`, `c-purple`, `c-teal`, `c-gray`, `c-green`, `c-red`) for colors that auto-adapt to light/dark mode.

Each connection is rendered as a `<path>` or series of `<line>` elements — ALL right-angled:
```typescript
// Example: vertical down, horizontal right, vertical down
function rightAnglePath(x1: number, y1: number, x2: number, y2: number, midY: number): string {
  return `M${x1} ${y1} L${x1} ${midY} L${x2} ${midY} L${x2} ${y2}`;
}
```

## Integration

Add a "Flow Diagram" tab or toggle in the code viewer for FB artifacts. When the engineer selects an FB artifact:

1. Parse the SCL content using `parseFbFlow(sclContent: string): FbFlowDiagram[]`
2. Render using `<FbFlowRenderer diagrams={diagrams} />`
3. Toggle between "Code" view (Monaco editor) and "Flow" view (diagrams)

For LAD artifacts, the flow diagram is not applicable (LAD is already visual). Only show it for SCL FBs.

## Test cases

Test with these three FBs in order of complexity:

1. **PE_Sensor** — simple: 5 inputs, 4 outputs, two timers, one self-hold latch, one IF/ELSIF status
2. **ControlMotor** — medium: 15 inputs, 6 outputs, mode selector CASE, direction split, fault latching with reset, status word resolution
3. **ControlConveyor** — complex: 9 inputs, 17 outputs, state machine with 4 states, direction split, timeout/jam/endSensor fault detection, reset path, remaining timeout calculation

The PE_Sensor diagram should produce 2 diagram groups:
- Signal flow: 3 columns (#_SensorDlyOn, #_SensorDlyOff, #_SensorDlyOnOff)
- Status: 1 column (#_Status) shown as truth table

The ControlMotor diagram should produce 3 diagram groups:
- Run commands: 2 columns (#fwdRun, #revRun) — mode selector → run permit → direction split
- Faults: 4 columns (#runFault, #stopFault latches) + 2 direct latches (#eStop, #extFault) → OR → #generalFault, plus reset path
- Status: 1 column (#status) — priority table

The ControlConveyor diagram should produce 3 diagram groups:
- Run commands: 2 columns (#runForward, #runReverse) — run edge + permit → direction split → monitoring → output
- Faults: 4 columns (#timeoutFault, #jamFault, #endSensorFault, #eStopActive) → OR → #faulted/#error, plus reset path
- State outputs: 6 columns (#busy, #idle, #runningForward, #runningReverse, #currentDirection, #remainingTimeout)
